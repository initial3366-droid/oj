# 两阶段通信题最小示例

发送方读取 `ENCODE\n37\n`，输出 `37\n`（3 个 UTF-8 字节）。
信道读取消息及公开加数 `5`，生成 `DECODE\n37 5\n`。
接收方在新沙箱中读取该输入并输出 `42\n`，最终检查器检查答案。

后台新建题目时使用“导入通信题包”，选择 `communication-example.zip`。
导入后默认是私有草稿；检查题面、消息上限、源码和测试点，再保存或发布。
编辑已有题目时，可切换到“通信题（两阶段）”，填写 `channel.cpp` 和 `checker.cpp`，上传 `data.zip`。
`communication.json` 是管理 API 的完整 communication 字段；其中源码为代码文本。
`problem.json` 是整题包元数据；其中源码为包内路径，两者不可混用。

普通测试数据 ZIP：`N.in`、`N.out`（或 `.ans`）、`N.public2.in`。
通信题答案和公开数据允许留空；信道与检查器必须自己支持这种情况。
选手只能获得题面及公开样例，隐藏输入、通信消息和裁判源码不会进入评测预览。

每个阶段单独执行语言倍率后的题目时间/内存限制，总览取两阶段最大值。
通信超过预算、空消息禁用、非法 UTF-8、信道返回 1/2、最终答案错误均为 WA；
选手编译失败为 CE，选手超时/内存超限/崩溃为 TLE/MLE/RE；
裁判编译失败、崩溃、超时或未生成 DECODE 标记为 SE。
信道和 checker 使用固定 C++17，沙箱限制为 5 秒 CPU、15 秒墙钟、256MB 内存。
stdout 必须是 UTF-8 文本；stderr 不计入通信预算，但受到平台输出安全上限约束。

C/C++、Python、Java 参考代码在本目录。自测可输入某一阶段完整输入；
完整流程需要提交评测。不要依靠全局变量或文件在两个阶段之间共享秘密。
